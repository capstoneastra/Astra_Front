추가로 정리한 것

- 시험 의뢰 목록: 큰 카드 → 한 줄 목록 + 상태 칩(건수 표시) + 검색. 기업 계정에는 '받은 의뢰' 전환을 숨김
- 장비 검색: 검색어·시험 종류·지역·기관 필터를 한 줄로, 카드에 핵심 사양 3개·이용료·가용 상태를 표시
- 업무 알림: 읽지 않은 알림 우선, 한 줄 목록
- 예약 캘린더: 칸 높이를 화면 높이에 맞춤, 필터는 버튼으로 펼침
- 보유 장비 관리: 등록 폼을 버튼으로 펼치도록 해서 목록이 먼저 보이게 함
- 기존 대시보드 목록 버튼에 브라우저 기본 버튼 모양(회색 배경·테두리)이 그대로 보이던 문제 수정

## 2. 소속별 첫 화면 설계 원칙

지금까지의 화면은 "기능을 나열"한 형태였습니다. 실무자는 로그인하자마자 **"오늘 내가 처리해야 할 것"**과 **"내 일이 어디까지 진행됐는지"**를 알고 싶어 합니다. 그래서 각 소속의 첫 화면을 아래 기준으로 다시 구성했습니다.

1. **첫 줄은 사람에게 말하듯** — "김지훈님, 오늘 확인할 일이 3건 있어요." 숫자 카드보다 먼저 읽힙니다.
2. **할 일은 행동 버튼과 함께** — 목록 행마다 "보완하기 / 일정 확인 / 검토하기"처럼 다음 행동을 적고, 기한(D-3)·경과일(2일 전)을 오른쪽에 둡니다.
3. **상태는 흐름으로** — 10개의 상태값을 6단계 파이프라인으로 묶어 "어디서 멈춰 있는지"가 보이게 합니다. 내가 처리해야 하는 단계에만 점(●)이 깜박입니다.
4. **역할마다 '주인공' 블록이 다름** — 같은 레이아웃에 숫자만 바꾸지 않고, 역할별로 가장 중요한 블록을 가장 큰 자리에 둡니다.

### 기업 (시험 의뢰자)

| 위치 | 블록 | 이유 |
| --- | --- | --- |
| 상단 | 의뢰 진행 파이프라인 (작성 중 → 접수·검토 → 보완 요청 → 일정 협의 → 예약 확정 → 완료) | "내 시험이 어디까지 왔나"가 가장 궁금함 |
| 메인 좌 | 지금 처리할 일 (보완 요청 D-day, 일정 제안 확인, 작성 중 의뢰) | 기업 쪽이 멈춰 있으면 전체 일정이 밀림 |
| 메인 우 | 다가오는 시험 (날짜 칩 + D-n) | 시료 준비·출장 계획 |
| 하단 | 장비 찾기(검색 + 시험 종류 칩) / 최근 AI 상담 | 새 시험을 시작하는 입구 |

### 기관 (장비 운영 담당)

| 위치 | 블록 | 이유 |
| --- | --- | --- |
| 상단 | 검토 대기 · 일정 협의 · 이번 주 시험 · 정보 갱신 필요 | 기관의 KPI는 '처리 속도'와 '장비 가동' |
| 메인 좌 | 검토할 의뢰 (접수 후 경과일, 3일 이상은 강조) | 응답 지연이 플랫폼 신뢰도를 떨어뜨림 |
| 메인 우 | 이번 주 장비 일정 (장비 × 7일 보드) | 실험실 운영자는 '장비 단위'로 일정을 봄 |
| 하단 | 보유 장비 상태 (가동률, 점검 중, 정보 갱신 필요) | 오래된 사양·이용료 정보는 잘못된 의뢰로 이어짐 |

### 대학 (연구실·센터 담당)

기관과 업무는 비슷하지만 **장비 일정이 가장 먼저** 보이도록 했습니다. 대학 장비는 학내 연구·수업과 외부 의뢰가 같은 장비를 나눠 쓰기 때문에, "이번 주에 비는 날이 있는지"가 의뢰 검토보다 먼저 필요합니다. 상단 지표도 '정보 갱신 필요' 대신 **평균 가동률**을 보여줍니다(공동활용 실적 보고와 직결).

### 관리자

| 위치 | 블록 | 이유 |
| --- | --- | --- |
| 상단 | 회원 승인 대기 · 기관 승인 대기 · 장비 정보 검증률 · 진행 중 의뢰 | |
| 메인 좌 | **승인 대기 목록에서 바로 승인/거절** | 관리자의 가장 반복적인 일. 화면 이동 없이 처리 |
| 메인 우 | 기관별 장비 정보 검증률 (낮은 순) | 데이터 품질이 낮은 기관부터 연락 |
| 하단 | 플랫폼 의뢰 흐름 | 어느 단계에서 의뢰가 쌓이는지 파악 |

## 3. "관리자 계정이 실제로 효율적인가"에 대한 의견

기존 구조에서는 관리자가 플랫폼의 **모든 가입을 한 명씩** 승인해야 하고, 거절할 때마다 사유를 직접 타이핑해야 했습니다. 회원 수가 늘면 관리자가 병목이 됩니다. 이번 화면 개선(대시보드 즉시 처리, 일괄 승인, 거절 사유 선택)으로 클릭 수는 줄였지만, 근본적으로는 **승인 권한을 나누는 것**을 권장합니다. 아래는 백엔드와 함께 검토할 제안입니다.

1. **기관 내 승인 위임** — 기관·대학이 한 번 승인되면, 같은 기관 소속 담당자의 가입은 그 기관의 대표 담당자가 승인. 플랫폼 관리자는 '새 기관 등록'만 처리.
2. **자동 검증 후 승인** — 기업: 사업자등록번호 상태 조회(국세청 API) 통과 시 자동 승인 / 연구자: 국가연구자번호 확인 통과 시 승인 대기 목록에서 '확인됨' 표시.
3. **관리자의 역할 재정의** — 승인 담당이 아니라 **데이터 품질·분쟁 조정 담당**. 장비 정보 검증률이 낮은 기관 알림, 3일 이상 검토되지 않은 의뢰 에스컬레이션, 반복 반려·취소 의뢰 모니터링 같은 운영 지표를 보는 역할이 더 가치가 큽니다.

## 4. 시연 데이터 (src/demo)

- 로그인 화면의 **시연 데이터로 둘러보기** 버튼으로 들어온 경우에만 axios adapter 가 `src/demo/server.ts` 로 응답합니다.
- 응답 형식은 `docs/api-spec.md` 의 envelope(`{ success, data }`)과 각 서비스의 검증 로직을 그대로 통과하도록 맞췄습니다.
- 기관·기업·장비 이름은 모두 가상의 이름입니다. 상태 변경은 메모리에만 반영되며 새로고침하면 초기화됩니다.
- 실제 로그인 흐름, 토큰 처리, 서비스 계약은 변경하지 않았습니다.
- 제거 방법: `src/demo/` 폴더 삭제 후, `src/api/client.ts` 의 `localWorkspaceAdapter` 를 이전처럼 `Promise.reject(...)` 로 되돌리고 `blockLocalWorkspaceRequests` 의 `setDemoUser` 호출 두 줄을 지웁니다.

## 5. 백엔드와 맞춰야 할 점

- 대시보드 `summary.upcomingReservations` 항목에 예약 상태(PROPOSED/CONFIRMED)를 포함하면 '이번 주 장비 일정'에서 확정/제안을 색으로 구분할 수 있습니다.
- 장비 목록 응답(`GET /equipment`)에 `specs` 일부(핵심 3개)를 포함하면 검색 카드에서 상세를 열지 않고도 사양 비교가 가능합니다.
- 의뢰 제출이 생성→저장→제출 3번 호출로 이뤄집니다. `POST /test-requests` 에 `content` 와 `submit: true` 를 함께 받는 API가 있으면 한 번으로 줄일 수 있습니다.
- 관리자 승인 위임(3절 1번)을 하려면 사용자에 '기관 대표 담당자' 역할(또는 플래그)이 필요합니다.

### 관리자 계정 생성·정보 수정 확인 결과

- **팀 API 명세(`docs/api-spec.md` §관리자)**: 회원은 가입 승인·거절·정지/해제만 있고, 관리자가 회원 계정을 만들거나 이름·이메일 등을 수정하는 API는 없습니다. 반대로 기관은 `POST /admin/organizations`(직접 등록, 바로 승인), `PATCH /admin/organizations/{id}`(정보 수정)가 있습니다.
- **유사 공공 시스템 사례**: 국가 연구시설 관련 정보시스템(예: 시험·연구용 LMO 정보시스템)도 이용자가 직접 가입하고, 소속기관 책임자나 운영기관이 승인·반려하는 구조이며, 운영자가 계정을 대신 만드는 흐름은 확인되지 않았습니다.
- 그래서 회원 계정 생성·개인정보 수정은 추가하지 않았습니다. 본인 인증(이메일·사업자번호·연구자번호)을 거치지 않은 계정이 생기고, 개인정보 변경 책임이 불분명해지기 때문입니다. 필요하다면 '정보 수정 요청' 같은 별도 절차를 백엔드와 먼저 정하는 것을 권장합니다.

### '보유 장비 상태'의 %는 무엇인가

장비 데이터의 `utilizationRate`(**가동률**)입니다. 장비를 쓸 수 있는 시간 중 실제 시험에 사용된 시간의 비율이며, 국가연구개발 시설·장비 표준지침에서도 가동률로 '활용 / 저활용 / 유휴' 장비를 구분합니다. 다만 현재 API 명세에는 계산 기간과 방식이 정의되어 있지 않고 예시 값도 `null`이므로, 백엔드와 다음을 정해야 합니다.

- 계산 기간 (예: 최근 12개월) 과 산출 방식 (예약 확정 시간 ÷ 운영 가능 시간), 또는 기관이 직접 입력하는 값인지
- 값이 없을 때 표시 — 지금은 '미등록'으로 표시

### 알림 링크 필드 제안

알림을 눌렀을 때 정확한 작업으로 이동하려면 서버 응답에 링크가 필요합니다(`backend-handoff.md` P2). 프론트는 아래 형식을 먼저 지원하며, 없으면 메시지 앞의 `[보완 요청]` 같은 분류로 화면을 추정합니다.

```json
{ "id": 1, "message": "[보완 요청] …", "isRead": false, "createdAt": "…",
  "link": { "type": "REQUEST", "id": 15 } }   // type: REQUEST | USER_APPROVAL | ORGANIZATION_APPROVAL | EQUIPMENT
```

### ① 조건 정하기
- '정리된 조건' 아래 **시험 종류**: 가로 스크롤 칩 → **줄바꿈되는 카드 격자**(이름 + 장비 n대, 고른 것 체크, AI가 고른 시험은 'AI 추천'). 휴대폰은 2열.
- 소제목 '시험 종류' / '○○ 조건(필수 n/m 입력)'으로 묶어 읽기 쉽게. [다시 쓰기]는 시험 종류 소제목 오른쪽으로.
- 검색창 아래 **파일 끌어다 놓기 칸**(눌러서 고르기도 가능, 최대 5개).
  - txt·csv·md·json·tsv(200KB 이하)는 **AI가 내용을 읽어** 조건을 채움. 시험 종류를 아직 못 정했으면 넣자마자 해석.
  - 명세 §5 첨부 허용 파일(pdf·이미지·xlsx/xls/csv·docx/doc·hwp/hwpx·pptx·txt·zip, 20MB 이하)은 ③에서 **의뢰서 첨부**로 올림. 허용되지 않는 파일은 빼고 이유를 안내.
  - 파일마다 'AI가 읽음' / '첨부' / '첨부됨' 표시. 대시보드에서 넘어온 PDF 등은 파일 자체가 없어 '이름만'으로 표시.
  - 칸 밖에 잘못 떨어뜨려도 브라우저가 파일을 열며 작성 내용이 사라지지 않게 막음.
