# 시험 의뢰 입력 간소화 및 진행 정보 통합

2026-11-24 · `feat/yeonji`. 기준: `docs/api-spec.md` §3·5·6·7, 사용자 피드백 및 첨부 비교표. 로그인·회원가입·백엔드 코드는 수정하지 않는다.

## 구현한 흐름

장비 선택 → 기존 상담을 가져오거나 시험 목적을 한 번 설명 → 서버 의뢰서 생성 → 누락 항목만 보완 → 전체 내용 확인·수정 → 사용자 직접 제출.

- 기존 `requirementId`는 `POST /test-requests/ai-draft`에 연결한다. 상담만 있으면 기존 세션의 `/requirement`를 호출한다.
- 새 설명은 `POST /chat/sessions` → `POST /chat/sessions/{id}/messages` → `POST /chat/sessions/{id}/requirement` → `POST /test-requests/ai-draft` 순서로 보낸다. 성공한 단계는 페이지 내 재시도에서 재사용한다. 생성 뒤 사용자 편집을 AI가 덮어쓰지 않는다.
- ‘직접 작성’ 유지. 장비·신청자 등 알려진 정보는 양쪽 모두 반영한다. 모르는 시료명·비용·일정·수량은 추정하지 않는다.
- 실사용자는 명세대로 신청자로 초기화한다. 회계 담당자는 추정하지 않으며 ‘신청자와 동일’을 직접 눌러 복사한다. 실사용자도 같은 버튼으로 수정 가능하다.
- 누락 항목은 입력칸, 채워진 정보는 요약으로 표시한다. ‘전체 항목 수정’으로 모든 칸을 연다. 입력 중인 칸은 값이 유효해져도 사라지지 않는다.
- 시작일 입력 후 ‘당일 시험’을 누르면 종료일을 복사한다. 예약 확정은 아니다.
- 시험조건·미확인 상태는 수정 가능. 성적서 종류·청구 방법·시료 처리·책임자는 선택 영역에 두고 기관 보완 절차를 유지한다.
- 필수값·공백·이메일·유효 날짜·기간 역전·수량·담당자 연락처(전화 또는 이메일)를 검사한다. 내용을 수정하면 제출 확인은 해제된다.
- 수동 초안 저장 버튼 없이 기존 `PUT /test-requests/{id}/draft` → `POST /test-requests/{id}/submit`을 유지한다. 저장 뒤 제출에 실패해도 새 version과 편집 내용을 보존한다. 충돌은 오류로 안내하고 최신 정보를 조회한다. 임의 자동 제출·충돌 무시는 하지 않는다.

주요 파일: `components/workflow/RequestComposer.tsx`, `domain/requestComposer.ts`, `services/requestService.ts`, `services/contracts.ts`. 기존 `Reservation.tsx` 경로는 재내보내기로 유지한다.

## 첨부 표를 반영한 의뢰 상세

기존 상세 안에 네 영역을 모았다. 새 전체 진행 API 없이 `GET /test-requests/{id}`만 사용한다.

| 영역 | 표시 | 한계 |
|---|---|---|
| 시료·진행 | 시료명·수량·준비일·처리 방법·의뢰 상태 | 배송·수령 상태 API가 없으므로 추정 금지 |
| 일정 | CONFIRMED 예약 또는 희망일·미확정 안내, Asia/Seoul 표시 | 제안·확정·시험 완료 구분 |
| 결과·성적서 | `result.summary`, `reportNo`, `reportUrl` | 미등록은 대기. http/https 링크만 제공 |
| 이용료·증빙 준비 | `estimatedFee`, 회계 담당자, 희망 청구 방법 | 예상액은 납부액이 아님. 납부·정산·지원금 API 미제공 안내 |

기존 기관 검토·보완·예약 컨트롤과 이력은 유지한다. 새 결제·지원금·세금계산서 발급 API는 만들지 않았다. 예상 이용료/결과는 서버 값이 있을 때 표시하며 등록·수정 화면은 이번 변경 범위가 아니다.

## Gemini 및 백엔드 확인 사항

프론트는 기존 ASTRA AI API만 호출한다. Gemini SDK·브라우저 API 키·`VITE_*` 비밀키를 추가하지 않는다. 제공자 선택, Gemini 키 보관·호출, structured output 검증은 백엔드에서 처리해야 한다. 프론트만 바꿔 Gemini 연결 완료로 표시하지 않는다.

1. 배포 API 주소·CORS, 상담/조건/AI 초안 API의 실제 가용 여부 및 Gemini 사용 여부.
2. 원문에서 확인한 시료명·수량·규격·희망 기간을 content의 정확한 키로 옮기고 불확실한 값은 비우는지 확인.
3. 초안 `actualUser/accounting`, AI 메모, 저장 응답 version, 제출 오류 `details.missingItems` 실제 응답 확인.
4. 상세 `estimatedFee/result/reservations`, 성적서 다운로드 권한·링크 정책 및 추후 첨부 계약 확인.
5. 결제·실납부·증빙·지원금은 별도 사업 범위/API 설계 필요. 비교표의 목표를 구현 완료로 표시하지 않음.

## 검증

- `node scripts/check-request-composer.mjs`: 알려진 정보만 채움, 원본 비변경, 직접 수정 보존, 공백/날짜/기간/수량/이메일/연락처 검사, DEMO 제출 필수 항목 검사.
- 개발 브라우저: 실제 DEMO에서 새 설명 → 자동 초안 → 누락 보완 → 동일 담당자/당일 시험 → 수정 시 확인 해제 → 명시적 제출을 확인. 테스트에서 제출 단계만 실패시켜 저장된 새 version으로 재시도·성공 및 편집 내용 보존을 확인했다.
- 실제 API 실패를 DEMO 성공으로 바꾸지 않는다. 실제 Gemini 분석·기관 접수·성적서·결제 통합 검증은 **백엔드 미배포로 테스트 불가**다.
- TypeScript·Vite production 빌드·ESLint·인증 코드 보존 검사를 통과했다. 5가지 데스크톱 해상도의 기존 캘린더/챗봇 회귀 검증과 390px 의뢰 상세의 가로 넘침 없음도 확인했다. 실제 형태의 결과·예상 이용료(0원 포함) 표시와 비허용 성적서 URL 차단을 정적 렌더링으로 검증했다. 기존 Three.js 분리 청크의 500kB 경고는 남는다.
