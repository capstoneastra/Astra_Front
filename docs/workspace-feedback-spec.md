# ASTRA 사용성 피드백 반영 및 회원별 업무 화면 명세

최신 후속 구현: 사용자가 로그인·회원별 화면을 실제로 요청하여 [회원별 업무 공간·상호 대여·DEMO 결제](role-workspace-payment.md)를 반영했다. 아래 ‘회원별 화면은 제안만’이라는 초기 범위보다 후속 문서를 우선한다. 기존 PDF는 초기 기획 제안이며 현재 구현/결제 범위와 구분한다.

작성: 2026-11-23 · 브랜치 `feat/yeonji`

2026-11-24 추가 확인: 첨부한 기업·기관 제안서 7쪽을 시각적으로 대조했다. 기존 구성은 유지하고 관리자 운영 대시보드·메뉴·제외 기능을 별도 페이지로 보완한 [8쪽 PDF](ASTRA_기업_기관_화면구성_제안서.pdf)를 제공한다. 회원별 화면 재배치와 로그인 통합은 여전히 제안 범위다. 실제 UI에는 위성 장면 위 통신 궤적·발신 파동, AI 패널 등장·장비 선택 강조를 추가했다. 불필요한 설명 배너와 수동 초안 저장 버튼을 다시 추가하지 않는다. 개발 시연 데이터 복원은 별도 요청에 따른 [DEMO 모드](demo-mode.md)에서만 적용한다.

기준: [현재 API 명세](api-spec.md), [15개 기능 명세](functional-spec.md), [연동 인수인계](backend-handoff.md), 현재 React·TypeScript 코드. 이 문서는 로그인·회원가입 화면의 제작·병합을 포함하지 않는다. 기존 인증 파일·세션·토큰·권한 코드는 보존하며, **아래 회원별 화면 재구성은 제안 명세로만 작성**한다. 화면 메뉴를 실제로 재배치하거나 새 인증 우회를 만들지 않는다.

**초안 저장 버튼 제거 ≠ 서버 DRAFT 제거.** API 명세상 의뢰 생성 및 AI 자동 작성은 DRAFT를 만들고, `PUT /test-requests/{id}/draft` 후 `POST /test-requests/{id}/submit`으로 제출한다. 이 계약과 AI 자동 추진의 초안 종료·사용자 최종 승인 정책은 그대로 둔다. 임의의 단일 제출 API나 자동 제출을 추가하지 않는다.

검색 상세는 기존 모달 안에서 표시한다. 후속 업무는 기존 해시 경로를 유지하고 React Router의 계정 범위 상태에 `origin: search` 및 검색 상태를 보존한다. 독립 사이드바 메뉴로 직접 들어가면 검색 맥락 없이 해당 페이지가 열린다. 메뉴 표시 맥락은 실제 접근 권한을 대체하지 않는다.

캘린더는 데스크톱 1024px 이상·높이 650px 이상에서 화면 높이에 맞춘다. 낮은 데스크톱 화면에는 날짜당 일정 1개와 '+N건', 넉넉한 화면에는 2개와 '+N건'을 표시하며 세부 장비·기관·시간은 날짜 상세에서 확인한다. 더 작은 화면은 내용을 잘라 숨기지 않고 자연스러운 스크롤을 허용한다. 오류 시 빈 달력 틀은 유지하되 예약 조회 대기임을 명시하고 날짜별 예약 조작은 막는다.

## 2. 회원별 화면 설계 원칙 — 후속 통합용

화면 기본값은 사용자의 주 업무에 맞게 다르게 둔다. 이는 서버 권한을 역할명만으로 축소하거나 확대하는 규칙이 아니다.

- 기업: 필요한 시험을 찾아 의뢰하고 보완·일정을 확인하는 **의뢰자 중심**.
- 기관·대학 담당자: 보유 장비와 들어온 의뢰를 검토하고 예약을 관리하는 **장비 보유자 중심**.
- 관리자: 승인·데이터 품질·운영을 처리하는 **운영자 중심**. 기업용 상담·신규 의뢰 메뉴까지 기본 노출하지 않는다.

최신 API §0-4는 기업·기관·대학 모두 의뢰자가 될 수 있고, 같은 조직 장비의 보유자가 될 수 있다고 명시한다. 기업도 자기 조직 장비를 관리할 수 있으며 기관도 외부 장비에 의뢰할 수 있다. 따라서 “기업은 관리 기능 영구 금지/기관은 의뢰 영구 금지”로 구현하면 안 된다. **역할별 기본 메뉴 + 서버에서 확인한 소속·소유권에 따른 보조 업무**로 설계한다. 자기 조직 장비에는 의뢰하지 않는다.

현재 `src/auth/permissions.ts`는 역할 기반으로 기업에 기관 업무를, 기관에 일부 의뢰자 업무를 제한한다. 이 차이는 이번 작업에서 변경하지 않으며 로그인 통합 팀·백엔드와 협의 후 별도로 반영한다. API 명세의 일부 과거 설명과 최신 조직 정책이 충돌하는 부분은 [인수인계](backend-handoff.md)를 따른다.

## 3. 기본 메뉴 구성안

| 구분 | 기본 사이드바 | 보조 진입 | 기본 화면에서 제외 |
|---|---|---|---|
| 기업 | 내 업무 대시보드, 시험장비 검색, 내 시험 의뢰, 내 예약 캘린더, 업무 알림 | 검색 안 장비 비교·시험정보·시뮬레이션, AI 상담/자동 추진 공통 런처, 조건 분석·매칭 | 회원 승인·전체 DB 운영·타 기관 접수 의뢰 |
| 기관 | 기관 업무 대시보드, 보유 장비 관리, 접수 의뢰 검토·보완, 기관 예약 캘린더, 업무 알림 | 장비 검색·시험정보·중복 장비 검토, 권한 확인 후 외부 장비 의뢰자 업무 | 일반 기업용 신규 의뢰·AI 자동 추진을 기관 기본 메뉴에 혼재시키지 않음, 회원 승인 |
| 관리자 | 운영 대시보드, 회원·조직 승인 관리, 장비 데이터 관리, 중복·갱신 검토, 예약 모니터링, 운영 알림 | 장비·의뢰 상세 운영 조회, 사유·기록을 남기는 관리자 처리 | 기업 AI 상담·의뢰 생성·시뮬레이션·'내 의뢰'를 기본 메뉴에서 제외 |

기업이 장비 보유 업무도 수행하면 서버가 허용한 범위에서 '우리 조직 장비 관리' 작업공간을 추가한다. 기관이 의뢰자로 이용하면 '외부 장비 이용' 작업공간으로 전환한다. 이것은 역할을 바꾸는 로그인 선택기가 아니며, 메뉴·조회 박스·데이터 범위만 전환한다. 서버가 기능 허용 여부를 내려주지 않으면 프론트가 임의 capability를 발명하지 말고 최종 정책을 협의한다.

## 4. 각 대시보드의 내용과 우선 행동

| 대상 | KPI | 주요 패널 | 주요 행동 | 조회 계약 |
|---|---|---|---|---|
| 기업 | 내 제출 의뢰·보완 필요·일정 협의·확정 예약 | 큰 장비 검색, 보완 요청, 다가오는 시험 | 장비 찾기, 보완 제출, 일정 확인 | `GET /dashboard/summary?view=REQUESTER`, `GET /test-requests?box=SENT` |
| 기관 | 소속 장비·신규/재제출·검토 중·예약 협의 | 접수 대기 큐, 장비 점유, 보완 회신, 갱신 필요 | 검토 시작, 보완 요청, 일정 검토, 장비 수정 | `GET /dashboard/summary?view=PROVIDER`, `GET /test-requests?box=RECEIVED` |
| 관리자 | 승인 대기 회원·미승인 조직·장비 갱신 현황 | 승인 큐, 데이터 검증/중복, 운영 알림 | 승인/거절/정지, 조직 검증, 데이터 정비 | `GET /dashboard/summary`, `GET /admin/users`, `GET /admin/organizations` |

API에 없는 지표는 '집계 준비 중' 또는 숨김으로 처리한다. 기존 `dataAvailable`이 false인 집계를 0으로 표현하지 않는다. 모든 화면을 같은 KPI·같은 AI/검색 히어로로 복제하지 않는다. 기관은 업무 큐, 관리자는 승인/데이터 큐를 중심으로 배치한다.

## 6. 데이터 범위와 상태별 행동

| 상황 | 화면 행동 | 서버 확인 |
|---|---|---|
| 기업 의뢰 목록/상세 | 본인이 보낸 의뢰만 | `box=SENT`, 의뢰자 ID 검사. 다른 기업 ID는 403 |
| 기관 접수 목록/상세 | 자기 조직 장비로 들어온 제출 의뢰만 | `box=RECEIVED`, 의뢰 institutionId와 소속 organizationId 검사 |
| 장비 수정 | 자기 조직 장비만 | `GET /users/me` 소속과 장비 보유 조직, 변경 API의 서버 소유권 검사 |
| 기업/기관 일정 | 각 업무 박스의 조회 가능한 의뢰 예약만 | 의뢰 목록→상세 및 예약 API의 서버 검사 |
| 장비 점유 | 확정 시간 구간만 공유 | `GET /equipment/{id}/reservations`, 타 기업 제목·기업명 등 비공개 데이터 미노출 |
| 관리자 처리 | 필요 작업만 별도 운영 화면에 제공 | ADMIN 검사, 변경 이력. 메뉴 숨김은 권한 검사가 아님 |

- 의뢰자: DRAFT에서 내용 확인 후 제출, SUPPLEMENT_REQUESTED에서 보완 답변·재제출, SCHEDULING에서 일정 제안. CONFIRMED는 조회·명세상 허용된 취소만.
- 보유자: SUBMITTED/RESUBMITTED에서 검토 시작, UNDER_REVIEW에서 보완/통과/반려, SCHEDULING에서 제안/대안/확정. CONFIRMED 이후 결과 등록 및 완료 처리는 명세 상태 전이를 따른다.
- 예약: PROPOSED=제안, COUNTER_PROPOSED=대안, CONFIRMED=확정, CANCELED=취소. 제안을 완료/확정처럼 표시하지 않는다. version·409 충돌 및 재조회 유지.
- 관리자 예약 확정 대행 등은 마스터 API 권한이 있더라도 기본 UI에 섞지 않고 운영 사유·이력 정책을 먼저 합의한다.

## 7. 로그인 통합 팀에 전달할 연결 사항

로그인 화면 구현·디자인·계정 발급은 담당 팀의 작업이다. 이 문서는 새로운 인증 API를 제안하지 않는다.

1. 기존 `GET /users/me`의 실제 역할·조직·계정 상태 필드를 확인해 공통 AuthContext로 전달한다. 로그인 화면에서 선택한 유형은 권한 근거가 아니다.
2. 인증 확인 중 내부 데이터를 그리지 않고 기존 로딩·보호 경로를 유지한다. 비회원 401, 권한/소유권 불일치 403을 유지한다.
3. 인증 이후 기업=의뢰자, 기관=보유자, 관리자=운영 화면으로 연결한다. 대시보드 view·의뢰 box를 명시하고 계정별 쿼리 키를 분리한다.
4. 소속/역할이 바뀌거나 로그아웃되면 검색 맥락·비교 장비·열린 상세·대화 등 전 계정의 비공개 화면 상태를 재사용하지 않는다.
5. 기존 프론트의 역할 제한과 최신 조직 정책 차이를 해결한 뒤 메뉴 가시성·보호 경로·서버 검사를 함께 검증한다. 이번에는 권한 코드를 변경하지 않는다.

## 8. 후속 구현 순서 및 검증

1. 로그인 통합 후 실제 세션 정보 확인 → 역할별 기본 작업공간 및 사이드바 분리.
2. 기업 REQUESTER/SENT, 기관 PROVIDER/RECEIVED, 관리자 운영 조회 범위를 API 담당자와 확정.
3. 공통 페이지는 재사용하되 대시보드 콘텐츠·목록 행동·빈 상태·주요 버튼을 업무별로 다르게 구성.
4. 보유자/의뢰자 겸업 전환은 서버 소유권 정책 합의 후 추가. 새 역할이나 미정의 API를 발명하지 않음.
5. 비회원, 다른 기업/기관 ID, 정지 계정, 역할 변경, 직접 URL, 예약 충돌을 실서버로 검증.

현재 백엔드의 실제 데이터·권한·상태 전이 통합 검증은 **백엔드 미배포로 테스트 불가**다. 화면 검증에 사용하는 별도 테스트 fixture는 제품 데이터나 Mock API로 포함하지 않는다. 실제 연동 완료로 보고하지 않는다.

UI 검증 대상은 1920×1080, 1536×864, 1366×768, 1280×720, 1024×768 및 모바일 390px이다. 검색 상태 복귀·동일 결과 영역·비교 추가/제외·챗봇 버튼 숨김/복원·입력 유지·그래프 전용 표시·캘린더 6주·클릭 피드백·모션 감소·로그인 파일 불변을 확인한다.
